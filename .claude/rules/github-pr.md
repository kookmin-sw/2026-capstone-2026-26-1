# PR 작성 규칙

이 저장소(모노레포 루트 `2026-capstone-26`)의 `.github/pull_request_template.md`가
`backend/`, `android/` 작업 공용 PR 템플릿이다. GitHub은 저장소 루트의 `.github/`만
인식하므로, `backend/`나 `android/` 어느 쪽에서 작업하든 이 루트 템플릿이 자동으로 채워진다.

[중요] 사용자가 pr 작성을 요청하면 우선 PR 초안을 작성하여 사용자에게 제공한다.

- 이때 PR 본문 마크다운 전체를 대화창에 그대로 출력하지 않는다. 스크래치패드(세션의 임시 파일
  디렉터리)에 `.md` 파일로 작성하고, 그 파일 경로만 짧게 안내한다.
- 사용자가 그 파일을 직접 열어 수정할 수 있다는 전제로 대기한다.
  "올려줘"/"게시해줘"처럼 명시적으로 게시를 지시받으면, 그 시점에 파일을 다시 읽어(사용자가 수정했을 수 있으므로 항상 최신 내용을 반영)
  `gh pr create --body-file <경로>`로 그대로
  게시한다. 이미 알고 있는 이전 버전 내용을 임의로 다시 쓰지 않는다.
- 명시적 게시 지시 전까지는 `gh pr create`를 절대 실행하지 않는다.

## 병합 방식

기존 관례(일반 merge, squash 아님)를 유지한다. 커밋 이력을 보존하는 방식이므로,
PR에 올라가는 개별 커밋 메시지도 [git-commit.md](git-commit.md) 형식을 지켜야
merge 후 로그가 지저분해지지 않는다.

## 라벨

작업 대상 모듈에 따라 라벨을 다르게 붙인다.

- `backend/` 아래 작업으로 만드는 PR → 항상 `💻BE` 라벨
- `android/` 아래 작업으로 만드는 PR → 항상 `📱AND` 라벨
- `backend`와 `android` 작업이 동시에 진행될 경우 `💻BE` 라벨과 `📱AND` 라벨을 모두 붙인다.

PR 템플릿은 프론트매터가 없어 라벨을 지정할 방법이 없으므로, `gh pr create --label "💻BE"` /
`gh pr create --label "📱AND"`처럼 직접 지정해야 한다.

## 제목 형식

```
<type> : <한국어 요약>
```

## 본문 구조 (실제 템플릿)

```markdown
## 🛰️ Issue Number

## 🪐 작업 내용

## 📚 추가 리팩토링 가능성
```

- **Issue Number**: 관련 이슈 번호(`#<번호>`)를 적는다. 템플릿 자체는 GitHub의 자동 종료
  키워드를 쓰지 않으므로, PR 병합과 동시에 이슈를 자동으로 닫고 싶으면 `closes #<번호>`처럼
  종료 키워드를 명시적으로 함께 적어야 한다. 이슈와 무관한 PR(잡일성 chore 등)이면 비워둔다.
- **작업 내용**: **이 PR로 어떤 서비스·기능·리소스를 갖추게
  됐는지**를 기준으로 쓴다. 아래 "작업 내용 서술 관점" 참고.
- **추가 리팩토링 가능성**: 이번 PR 범위 밖이지만 발견한 개선점을 남긴다. `backend/`
  작업이라면 `backend/.claude/CLAUDE.md`의 "포트폴리오 관점 제안" 규칙과 같은 맥락 —
  임의로 고치지 말고 여기에 적어 다음 작업으로 넘긴다.

## 작업 내용 서술 관점

"작업 내용"은 코드가 무엇을 어떻게 바꿨는지가 아니라 **완성된 결과물(어떤 서비스·기능·
리소스를 갖추게 됐는지)** 기준으로 쓴다.

- **`### 배경`을 맨 앞에 짧게 둔다.** 왜 이 작업이 필요했는지(무슨 문제·계기가 있었는지)를
  1~3문장으로만 소개하고 바로 다음 섹션(리소스·기능 목록)으로 넘어간다. 배경 자체를
  분석하거나 길게 풀어쓰지 않는다 — 자세한 원인·과정은 이미 있는 관련 문서로 링크하고,
  여기서는 "왜"를 인지시키는 역할만 한다.
- **변경 이력·코드 diff 설명을 최소화한다.** "처음엔 A였다가 B로 바꿨다가 다시 C로 고쳤다"
  같은 과정 서술이나 `git diff` 요약을 늘어놓지 않는다. 지금 결과적으로 무엇이 구축·도입
  됐는지만 남긴다.
- **리소스·기능 단위로 섹션을 나눈다.** 여러 항목이 있으면 시간순이 아니라 "1. 메모리 관측
  체계", "2. 호스트 메모리 안전망"처럼 갖추게 된 기능·리소스 단위로 나눠, 각각 무엇을
  갖추게 됐는지 한두 줄로 압축한다.
- **산출·계산 과정은 결과만 남기고 문서로 넘긴다.** 수치를 산출한 공식, 여러 단계 재계산,
  후보 비교 같은 과정은 본문에 풀어쓰지 않는다. 최종 값과 "산출 과정은 문서 참고" 링크만
  남긴다.
- **단, 실측 효과(적용 전후 비교 수치)는 예외로 그대로 남긴다.** 이건 과정이 아니라 성과이므로
  구체적 수치(예: "적용 4분 후 CPU 80%→2%대")를 압축하지 않는다.

## 작성 톤 & 가독성

- "작업 내용"이 길어지면 한 덩어리로 쓰지 말고 `###` 하위 섹션(예: `### 배경`, `### 변경 사항`,
  `### 테스트`)이나 `-` bullet으로 쪼갠다. 리뷰어가 스크롤 없이 훑을 수 있는 길이를 기준으로
  삼는다.
