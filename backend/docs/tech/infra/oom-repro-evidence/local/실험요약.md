# OOM 재현 실측 요약

로컬(Windows11 + Docker Desktop/WSL2)에서 t2.micro OOM 조건을 재현하며 확보한 실측 지표.
OOM 대응 옵션을 제거한 이미지(`Dockerfile.oom-repro`, ENTRYPOINT
`java -XX:MaxRAM=955m -XX:NativeMemoryTracking=summary -jar app.jar`)로 두 갈래 실험했다.

## 실험 A — 충실 조건 footprint → 955 산술 (핵심)

`--cpus=1`(t2.micro 1 vCPU 파리티) + `MaxRAM=955m`, **메모리 무제약**. 이 조건에서 JVM은
**SerialGC**를 선택(t2.micro와 동일). 메모리를 물리적으로 안 줄인 이유는 WSL2+Docker 엔진
오버헤드(~520MB)가 EC2 OS+dockerd(~230MB)보다 커서 VM 재현이 왜곡되기 때문 — footprint만 재고
산술은 EC2 실측 고정비로 한다. (원시: `NMT-힙논힙분해.txt`, `앱메모리-스냅샷.txt`)

| 항목 | 값 |
|---|---:|
| 힙 상한 | 240 MiB (=MaxRAM 955의 25%) |
| 논힙 committed | ≈197 MiB (Metaspace 90·Symbol 40·Code 25·Class 16·Shared 13·Thread 3·GC 0.8) |
| 앱 정착 anon | 456 MiB |
| **앱 기동 피크** | **619 MiB** |

**955 산술(swap 0):** 619(앱) + 6(redis) + 230(OS/dockerd, EC2 실측) = **855 MiB = 89%** →
**넘지 않음.** 단발 부팅은 예산의 89%를 swap 0으로 채운 "칼날 위" 상태다.

- **CPU 파리티 보정이 결론을 뒤집음:** 8 vCPU에선 피크 729(G1 remembered-set 59MiB + 컴파일러
  스레드) → 965>955로 "초과"라 **오판**. 1 vCPU+SerialGC(GC 0.8MiB)로 맞추면 619 → 855로 미달.
- 이 측정은 t2.micro의 CPU 크레딧 스로틀→GC 기아를 재현 못 하므로 855는 **보수적 하한**.

## 실험 B — 커널 OOM-killer 킬 메커니즘 (보조)

`mem_limit=400m, memswap_limit=400m`(swap 0)으로 좁혀 무트래픽 부팅 → `Started` 전에 반복 OOM.
(원시: `커널-OOM-killer-로그.txt`)
- `Killed process (java) anon-rss:406120kB`, `memory: usage 409600kB = limit`, `swap: usage 0kB`.
- exit 137 + `restart: always` → RestartCount 16까지 죽음의 루프.
- **스코프 주의:** `constraint=CONSTRAINT_MEMCG`(내가 건 cgroup 한도). 운영 무경계 장애는 호스트
  전역 `CONSTRAINT_NONE`이므로, 실험 B는 "swap0→즉발 kill + restart 루프"라는 **메커니즘**을
  실증하는 것이지 "경계 없음→인스턴스 전역 전염" 스코프까지 재현한 건 아니다.
- 대조군 `mem_limit=700m` → 안정(RestartCount 0).

## 종합 결론

단발 부팅은 955 미만(89%, 실험 A)이며, swap 0 + 경계 부재 + `restart: always` 루프가 그 얇은
11%를 넘겨 OOM을 만든다. 실험 B가 그 kill·루프 메커니즘을 직접 포착했다. 상세 산술은
`955MB-초과여부-산술판정.md` 참고.
