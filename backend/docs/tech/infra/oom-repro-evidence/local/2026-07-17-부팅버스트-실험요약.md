# 실험 C — 부팅 버스트 힙 피크 실측 (2026-07-17)

## 배경

같은 날 오전 운영 EC2가 `mem_limit` 700m→640m 재산정 배포 직후 `OutOfMemoryError: Java
heap space`로 30초 간격 크래시 루프(412회)에 빠졌다. 원인은 힙 상한이 176MiB→160MiB로
줄어 부팅 버스트를 못 버틴 것으로 확정됐으나, 2026-07-13 실험(`실험요약.md`,
`955MB-초과여부-산술판정.md`)이 남긴 힙 사용량(68MiB)·논힙(197MiB) 수치는 **부팅이 끝나고
트래픽 없이 정착한 idle 스냅샷**이지 실제로 죽인 **부팅 버스트 순간의 라이브 피크**가
아니었다. 이 실험은 그 공백을 메워 `-XX:MaxRAMPercentage` 산출 근거를 마련한다.

## 실험 조건

- 이미지: `backend/Dockerfile` 무수정 원본(스크래치패드 사본으로 빌드, Windows 체크아웃
  CRLF 문제만 우회 — `sed -i 's/\r$//' gradlew` 추가, 프로덕션 Dockerfile 자체는 무수정).
- `--cpus=1` (t3.micro 1 vCPU 파리티, 2026-07-13 실험의 교훈 적용).
- 로컬 MySQL(`docker-compose.local.yml`, 3307)·Redis(6380) 사용, 운영 RDS 미접속(실행 전
  `DB_URL` grep으로 확인).
- `DDL_AUTO=create`(운영과 동일 — 매 부팅마다 스키마 DROP+CREATE).
- 더미 Firebase service-account JSON(자체 생성 RSA 키, 실제 프로젝트와 무관, 네트워크
  인증 없음) — 이미지 빌드 시 `--build-context`로 굽고 실행.
- `JAVA_TOOL_OPTIONS`로 계측 플래그 주입(엔트리포인트의 `-XX:+ExitOnOutOfMemoryError
  -XX:TieredStopAtLevel=1`는 그대로 유지).
- 5회 반복: run1은 빈 DB에 최초 CREATE, run2~5는 직전 run이 남긴 스키마 위에서
  DROP+CREATE(운영의 반복 재시작과 동일 조건).

## 계획 대비 방법론 변경 사항

1. **jcmd/NMT 미사용** — `eclipse-temurin:21-jre`에 `jcmd`가 없음을 재확인(2026-07-13
   실험 당시와 다름, 또는 실험 스코프가 달랐던 것으로 추정 — 원인 불명, 기록만 남김).
   대신 **GC 로그**(`-Xlog:gc*`, 힙 used/committed 추적)와 **cgroup
   `memory.current` 폴링**(~1초 간격, 전체 RSS 추적)만으로 측정. 논힙은
   `cgroup 피크 − GC로그 힙 committed`로 역산 — jcmd 없이도 필요한 수치를 얻었다.
2. **`-Xmx` 값 2단계 보정** — 최초 `-Xmx512m`(생성적 무제약)로는 GC가 단 한 번도 발생하지
   않아 피크 신호 자체가 없었다(에덴이 절대 안 참). `-Xmx300m`으로 캘리브레이션한 결과 힙
   committed가 290MiB까지 부풀어(300m 한계의 96.7%) 거의 OOM 직전까지 몰렸음을 확인, 최종
   측정은 여유를 더 준 **`-Xmx400m`**으로 진행했다.
3. **부팅 완료 판정 기준 변경** — 애초 `Started CapstoneApplication` 로그를 종료 신호로
   삼으려 했으나, 이 로그 이후에도 **region seed 5034건 벌크 삽입**이 11~19초간 이어지는
   걸 발견했다. 폴링 종료 기준을 `region seed initializer finished` 로그로 늘렸다.

## 핵심 발견 — 힙 폭증의 주범은 DDL이 아니라 region seed

GC 로그를 보면 스키마 생성이 끝나고 `Started CapstoneApplication`이 찍힌 시점까지는 힙이
90~100MiB대에서 완만했다. 그런데 그 직후 region seed(전국 법정동 5,034건) 벌크 삽입이
시작되자 **단 2초 만에 힙 사용량이 100MiB→231MiB로 치솟았다**(GC(60)~GC(66)). 2026-07-13
실험의 idle 스냅샷(68MiB)은 이 버스트가 완전히 끝난 뒤의 값이라 이 폭증을 놓쳤다.

## 측정 결과 (5회, `-Xmx400m`)

| run | 힙 used 피크(GC 직전) | 힙 committed 최대 | cgroup RSS 피크 |
|---|---:|---:|---:|
| 1 (create-only) | 231 MiB | 298 MiB | 453.65 MiB |
| 2 (drop+recreate) | 231 MiB | 297 MiB | 454.19 MiB |
| 3 | 231 MiB | 298 MiB | 453.02 MiB |
| 4 | 231 MiB | 298 MiB | 452.97 MiB |
| 5 | 231 MiB | 298 MiB | **455.28 MiB (최대)** |

5회 모두 힙 used 피크가 정확히 **231 MiB**로 수렴했고, cgroup RSS 피크도 452.97~455.28MiB
로 1% 이내 편차다. run1(create-only)과 run2~5(drop+recreate) 사이 유의미한 차이 없음 —
DROP TABLE은 메타데이터 작업이라 가볍고, region seed 벌크 삽입이 부팅 메모리 압박을
압도적으로 지배하기 때문으로 보인다. 이상치 없어 재실행 불필요.

논힙+오버헤드(cgroup 피크 − 힙 committed) 최대치: 455.28 − 298 = **157.3 MiB**.

전 구간 `OutOfMemoryError` 0건 — `-Xmx400m`은 이 워크로드에 충분한 여유였다.

## 남은 공백

- Docker Desktop/WSL2 로컬 환경이라 t3.micro 실기기의 CPU 크레딧 스로틀(GC 기아)은
  재현하지 못한다 — 2026-07-13 실험과 동일한 한계.
- region seed가 실제 운영 초회 배포 때도 매번 실행되는지(테이블이 비어있을 때만 도는지,
  아니면 매 재시작마다 무조건 도는지)는 이번 실험 범위 밖 — 코드 확인이 필요하다.
- 5회 모두 같은 로컬 MySQL 인스턴스·같은 호스트에서 측정했다 — RDS 네트워크 지연이 다른
  운영 환경에서는 벌크 삽입 타이밍/메모리 프로파일이 달라질 수 있다.
