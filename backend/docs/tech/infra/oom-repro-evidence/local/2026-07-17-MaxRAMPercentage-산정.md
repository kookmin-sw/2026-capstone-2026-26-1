# MaxRAMPercentage 산정 — 부팅 버스트 실측 기반 (2026-07-17)

`2026-07-17-부팅버스트-실험요약.md`의 5회 측정 결과로 `-XX:MaxRAMPercentage`를 산출한다.
`mem_limit=640m`은 고정값으로 다룬다 — `EC2 응답 불능 문제 해결하기.md` §2.4가 밝힌
호스트 예산(`230 OS + 40 redis + 640 app = 910 ≤ 913 물리`)을 되돌리지 않기 위함이다.

## 입력값 (실측)

| 항목 | 값 | 출처 |
|---|---:|---|
| H_peak (힙 used 피크, GC 직전) | 231 MiB | 5회 전부 동일 |
| other_peak (논힙+오버헤드, cgroup 피크 − 힙 committed 최대) | 157.3 MiB | run5 (cgroup 최대 455.28MiB − 힙 committed 298MiB) |

`other_peak`은 이미 실측된 cgroup RSS 피크에서 직접 역산한 값이라, 원래 계획에서 상정한
"NMT committed + 별도 버퍼" 두 항을 합친 것과 동급이다 — 추가 버퍼를 얹지 않는다.

## 마진 정책

`EC2 응답 불능 문제 해결하기.md`의 기존 관행(피크 × 1.3~1.5배)을 따르되 하한(1.3배)을
적용한다. 이 산정은 §2.3의 "물리 천장 자체를 넘어서는" 상황(마진을 포기해야 했던 이유)이
아니라 **고정된 640m 봉투 안에서 힙과 논힙의 몫을 재분배하는 문제**이므로, 관행을
포기할 이유가 없다.

```
heap_ceiling = H_peak × 1.3 = 231 × 1.3 = 300.3 MiB → 301 MiB(반올림)
```

## 640m 예산 검증

```
required = heap_ceiling + other_peak
         = 301 + 157.3
         = 458.3 MiB

640 MiB ≥ 458.3 MiB  →  여유 181.7 MiB (28.4%)
```

마진 압축(1.3배→1.1배) 불필요 — 여유가 충분하다.

## 권고값

```
-XX:MaxRAMPercentage=47.0     (= 301 / 640 × 100, 반올림)
또는 절대값: -Xmx301m
```

## 비교표

| 설정 | 힙 상한 | 근거 |
|---|---:|---|
| 현재(크래시 루프 원인) | 160 MiB | 640m × 25%(기본 ergonomics) |
| 이전(700m 시절, 안정 동작) | 175 MiB | 700m × 25% |
| 2026-07-13 실측(idle 스냅샷 기준) | 240 MiB | `-XX:MaxRAM=955m` × 25% ergonomics 상한(실사용 68MiB) |
| **이번 실측(부팅 버스트 피크 기준)** | **301 MiB** | H_peak(231MiB) × 1.3 |

새 값(301MiB)이 2026-07-13의 240MiB를 넘는다 — 이는 측정 오류가 아니라 **idle 스냅샷이
놓쳤던 region seed 벌크 삽입 버스트를 이번에 처음 포착**했기 때문이다(실험요약 참고).
같은 이유로 이 값은 "이상 신호"가 아니라 이번 실험이 메우려던 바로 그 공백의 답이다.

## 남은 판단

- 이 문서는 측정·산출·문서화까지만 다룬다. `backend/Dockerfile`/
  `docker-compose.prod.yml` 수정과 재배포는 범위 밖이며, 사용자가 이 수치를 검토한 뒤
  별도로 결정한다.
- 실제 반영 시에는 `-XX:MaxRAMPercentage=47.0`을 엔트리포인트에 추가하는 형태가 되며,
  기존 주석(현재 25% 기본값을 쓰는 이유를 설명한 부분)도 이 실측 근거로 갱신이 필요하다.
