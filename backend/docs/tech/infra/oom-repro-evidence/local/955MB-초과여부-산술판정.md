# t2.micro 충실 조건 footprint → 955MB 대비 산술 판정

## 실험 조건 (오염 변수 배제)

메모리를 물리적으로 제약하지 않고(= WSL2/Docker 엔진 오버헤드가 결론에 개입 못 함), t2.micro와
동일한 조건만 부여해 앱의 실제 footprint를 측정했다.

- `--cpus=1` : t2.micro 1 vCPU 파리티 (cgroup `cpu.max=100000 100000` → 1.00 CPU 확인)
- `-XX:MaxRAM=955m` : 힙 ergonomics·GC 선택을 955MB 기준으로 고정
- 결과 GC = **SerialGC** (인지 메모리 <1792MB → non-server-class, 실제 t2.micro와 동일)
- 이미지 = OOM 대응 옵션 제거본, 기동 23.5초(8 vCPU 11초 대비 느림 → CPU 제약 방증)

## 앱 footprint 실측 (1 vCPU)

| 구분 | 값 |
|---|---:|
| 힙 상한 (MaxHeapSize) | 240 MiB (=MaxRAM 955의 25%) |
| 논힙 committed | ≈197 MiB (Metaspace 90 · Symbol 40 · Code 25 · Class 16 · Shared 13 · Thread 3 · GC 0.8) |
| NMT Total committed | ≈437 MiB |
| 앱 정착 anon(회수불가) | 456 MiB |
| **앱 기동 피크 (cgroup memory.peak)** | **619 MiB** |

## 955MB 대비 산술 (swap 0)

기동 피크 시점에 물리 메모리에 함께 상주하는 것들의 합:

| 항목 | 값 | 출처 |
|---|---:|---|
| 앱 기동 피크 | 619 MiB | 로컬 1 vCPU 실측 |
| Redis | 6 MiB | 로컬 실측 |
| OS + dockerd | 230 MiB | **EC2 실측**(문서 고정비, WSL 520이 아님) |
| **합계** | **855 MiB** | |
| t2.micro 물리 | 955 MiB (swap 0) | |
| **여유** | **100 MiB (약 89% 사용)** | → **넘지 않음 (case B)** |

## 결론

**충실 조건 단발 부팅은 955MB를 넘지 않는다.** 예산의 약 **89%**를 swap 0으로 채운 "칼날 위"
상태다. 즉 "배포하면 부팅 자체로 즉시 터진다"가 아니라, 물리 천장까지 여유 100MB에 완충(swap)이
0인 극도로 불안정한 상태로 떠 있는 것이다. 이 얇은 여유를 실제로 넘긴 트리거는 문서가 이미
지목한 **`restart: always` 루프 / 재배포 동역학**이다(단발이 아니라 반복·중첩 스파이크).

### 정직성 노트 1 — CPU 파리티 보정이 결론을 뒤집었다

8 vCPU에서 측정하면 기동 피크가 729 MiB로 부풀어 `729+6+230 = 965 > 955`, 즉 "초과"라고 **잘못**
결론냈을 것이다. 원인은 CPU 수에 비례하는 JIT 컴파일러 스레드와, 8 vCPU에서 선택되는 **G1 GC의
remembered-set 구조(59 MiB)**다. t2.micro는 1 vCPU + SerialGC(GC 구조 0.8 MiB)이므로, 파리티를
맞추자 피크가 619로 내려가 결론이 "미달"로 바뀐다. → 파리티 보정 없이는 틀린 결론이 났다.

### 정직성 노트 2 — 이 측정이 재현 못 하는 실기기 요인 (보수적 하한)

t2.micro는 CPU 크레딧 소진 시 baseline(≈10%)으로 스로틀된다. 그러면 GC가 제때 못 돌아 힙이 더
높이 쌓일 수 있는데, 로컬은 1 vCPU라도 풀스피드라 이 GC 기아 효과를 재현하지 못한다. 따라서
실기기의 실제 피크는 이 측정(619)보다 **더 높았을 수 있으며**, 855 MiB는 **보수적 하한**이다.
