# EC2 응답 불능 문제 해결하기

[EC2 응답 불능 문제 분석.md](oom-repro-evidence/production/EC2%20응답%20불능%20문제%20분석.md)에서
규명한 27시간 livelock(응답불능)을 어떻게 해결했는지 정리한다. 해결책은 **호스트 계층의 swap
할당**과 **컨테이너 계층의 mem_limit 설정**, 서로 다른 지점을 막는 두 개의 방어선으로
구성된다. 이 문서는  **"왜 이 조치가 필요하고, 왜 이 수치인가"**에
초점을 둔다.

## 문제 요약

swap이 없는 t3.micro(913 MiB 가용)에 스프링 애플리케이션과 redis 이미지가 떠 있다가, 가용 메모리가 0에 가까워지자 커널이 회수할 수 있는 게 파일 캐시뿐이라 그것만
붙잡고 스캔을 반복하는 **리클레임 스래싱**에 빠졌다. CPU는 계속 바쁘지만 시스템은 27시간 동안
아무 진전도 없었다(자세한 메커니즘은 위 분석 문서 참고).

---

# 1부 — swap 할당

## 1.1 왜 swap을 할당해야 하는가

리눅스가 메모리 압박 상황에서 회수할 수 있는 페이지는 두 종류뿐이다.

| 종류                 | 내용                        | swap 없을 때                         |
|--------------------|---------------------------|-----------------------------------|
| 파일 백업(file-backed) | 실행 코드, 라이브러리, 페이지 캐시      | 회수 가능 — 디스크에 원본이 있어 버렸다가 다시 읽으면 됨 |
| **익명(anonymous)**  | **JVM 힙**, 스택, malloc 아레나 | **회수 절대 불가** — 내보낼 곳(swap)이 없음    |

이 서버에서 메모리를 가장 많이 쓰는 건 JVM 힙이고, 이건 전부 익명 페이지다. swap이 없으면
커널은 이 덩어리를 **단 1바이트도 건드릴 수 없고**, 남은 선택지는 상대적으로 작은 파일
캐시뿐이다. 파일 캐시를 내쫓으면 그 페이지는 대개 실행 중인 코드였다가 곧바로 다시
필요해지고, 다시 읽어오려면 메모리가 필요해 또 회수한다 — 회수 대상이 "지금 당장 다시
필요한 것"밖에 없는 무한 루프, 즉 리클레임 스래싱이다.

**swap은 이 루프의 절반이 원천 봉쇄된 상태를 푸는 것**이다. 익명 페이지도 회수 가능한 풀에
합류시켜, 커널이 실제로 선택지를 갖고 판단하게 만든다.

### 실측으로 확인된 효과

이 조치를 실제 EC2에 적용한 직후(livelock 재발 초기 단계에서), 4분 만에 상황이 뒤집혔다.

| 지표           | swap 적용 전 |     swap 적용 후 | 변화       |
|--------------|----------:|--------------:|----------|
| `available`  |    35 MiB |   **158 MiB** | 4.5배     |
| `buff/cache` |   112 MiB |   **247 MiB** | 2.2배     |
| `Swap used`  |         0 | **311.3 MiB** | —        |
| CPU          |     80.1% |       **2%대** | 회수 폭풍 종료 |

**앱의 메모리 사용량(RSS)은 이 전후로 전혀 줄지 않았다.** 커널이 익명 페이지 311 MiB를
swap으로 내보내자 그만큼의 RAM이 파일 캐시로 돌아왔고, 가용 메모리가 4.5배로 뛰었다. 이건
"그 익명 페이지들이 처음부터 회수 가능했지만 회수 수단이 없었을 뿐"이라는 걸 보여준다 — swap이
메모리를 늘려준 게 아니라, **이미 있던 메모리를 커널이 다시 굴릴 수 있게 만든 것**이다.

## 1.2 왜 2GB인가

**근거 1 — 통용되는 산정 기준.** 물리 RAM이 2GB 이하인 시스템은 swap을 RAM의 2배로 잡는 것이
일반적인 권장치다. t3.micro(1GiB)에 정확히 대입하면 2GB가 나온다.

**근거 2 — 실측 풋프린트 대비 충분한 배수.** swap의 역할은 상시 작업 공간이 아니라 "익명
페이지가 순간적으로 몰릴 때의 완충재"다. swap 적용 후 19시간 관측한 RAM+swap 합계 실측
최댓값은 app 최대 ~730 MiB + Redis 수십 MiB 수준으로, 2GB는 이를 **2.5배 이상 덮는다.**
회수 압박이 와도 스왑아웃할 대상이 부족해질 일이 구조적으로 없다.

**왜 더 크게 잡지 않는가.** gp3 루트 볼륨(20GB)에 여유가 있어 4GB, 8GB도 어렵지 않게 잡을 수
있지만, 그러지 않는다. swap은 공짜가 아니다 — 스왑 I/O는 결국 gp3 디스크 읽기/쓰기이고, 이
인스턴스의 gp3는 이미 지연이 병목이다(livelock 당시 페이지 폴트가 144 IOPS ≈ 6.9ms/req로
못박혀 있었다는 게 분석 문서의 핵심 증거 중 하나다). swap을 크게 잡을수록 "많이 스왑해도
된다"는 유혹이 생기는데, 실제로 자주 스와핑되면 그 지연이 고스란히 GC·응답 지연으로
전가된다. 그래서 크기는 "회수 불가 상태를 근본적으로 없앨 만큼"만 채우고, **얼마나 자주
쓰이는지는 크기가 아니라 `vm.swappiness`로 통제**한다(기본 60 → 10, 여유가 있어도 적극
스왑아웃하지 않도록). swap은 "평소엔 안 쓰이는 최후의 안전판"이어야지 상시 작업 공간이
되어서는 안 된다는 게 크기와 swappiness 두 결정을 관통하는 원칙이다.

# 2부 — 컨테이너 상한(mem_limit) 설정

## 2.1 왜 mem_limit을 설정해야 하는가

swap이 리클레임 스래싱 자체를 막아준다면, `mem_limit`은 **다른 종류의 실패, 즉 "한 컨테이너의
문제가 호스트 전체로 번지는 것"을 막는다.** 이 저장소에는 이 차이를 그대로 보여주는 실측
대조군이 있다.

| 사건                               | `mem_limit`         | 커널의 판정(`constraint`)                                | 결과                                        |
|----------------------------------|---------------------|-----------------------------------------------------|-------------------------------------------|
| 로컬 대조 실험                         | `mem_limit=400m` 설정 | `CONSTRAINT_MEMCG` — **그 컨테이너의 cgroup 안에서만** OOM 판정 | java 프로세스 하나만 죽고 `restart:always`로 즉시 재기동 |
| 운영 idle-OOM 사건(`oom-kill 관측.md`) | 없음(무경계)             | `CONSTRAINT_NONE` — **호스트 전역**에서 OOM-killer 발동      | 어떤 프로세스가 죽을지 커널의 전역 판단(`oom_score`)에 맡겨짐  |

`mem_limit`이 없으면 컨테이너 안 프로세스는 sshd·dockerd·SSM 에이전트 등 **호스트의 다른
모든 프로세스와 동등하게** 메모리를 두고 경쟁한다. 문제가 생겼을 때 그 실패가 어디까지
번질지 아무도 정해두지 않은 것과 같다. `mem_limit`은 리눅스 cgroup 메커니즘으로 그 컨테이너의
메모리를 호스트의 나머지와 **별도 회계 처리**하게 만들어, 한도를 넘겼을 때 커널이 강제
종료하는 대상을 **그 cgroup 안으로 한정**시킨다. 즉 `mem_limit`은 "얼마나 쓸지"를 정하는
옵션이라기보다, **"문제가 생겼을 때 피해 범위를 어디까지로 가둘지"를 미리 그어두는 경계선**에
가깝다.

### mem_limit이 JVM의 판단 정확도에도 영향을 준다

`mem_limit`이 없는 지금, JVM의 `UseContainerSupport`는 참조할 cgroup 한도가 없어 **호스트
RAM 전체(913 MiB)를 자기 몫으로 착각**하고 그 25%(228 MiB)를 힙 상한으로 잡는다. 하지만
그 913 MiB는 애초에 이 앱 혼자 쓸 수 있는 양이 아니다 — OS·dockerd·Redis·다른 에이전트가
이미 그중 상당 부분을 쓰고 있다. `mem_limit`을 걸면 JVM이 참조하는 "가용 메모리"가 호스트
전체가 아니라 **실제로 이 컨테이너에 배정된 몫**으로 정확해지고, 힙 사이징을 포함한 모든
컨테이너 인식 로직이 현실에 맞게 동작한다.

### 실패 모드를 "느린 재앙"에서 "빠른 복구"로 바꾼다

`mem_limit` + `-XX:+ExitOnOutOfMemoryError` + `restart:always`를 함께 쓰면, 설령 예산
산정이 틀리더라도 결과가 27시간짜리 응답불능이 아니라 **수 초짜리 재기동**으로 끝난다.
`mem_limit`이 없던 무방어 상태에서는 실패가 항상 호스트 전역으로 번질 위험을 안고
있었지만, 경계를 그어두면 실패의 최대 크기 자체가 줄어든다 — 이게 정확한 수치를 맞추는
것 이상으로 `mem_limit`을 설정해야 하는 이유다.

## 2.2 Redis `mem_limit` 재산정 — 캡스톤 프로젝트 규모 기준

App의 몫은 물리 예산에서 OS와 Redis를 뺀 나머지로 정하므로, **Redis를 먼저 정해야 App의
몫이 정해진다.**

이 프로젝트는 캡스톤 프로젝트로 실제 가입자 수가 매우 적어, 데이터 상한을 그 규모에 맞게 잡았다.

```
실측 기준(idle, 실토큰 0건):  4.5 MiB   ← Redis 프로세스 자체 오버헤드, 데이터 아님
캡스톤 규모 추정: RefreshToken 항목당 300~700B(토큰 문자열+키+Redis 내부 오버헤드)
                수백~1000명을 가정해도 총 데이터는 수백 KB~1 MiB 수준
```

```
maxmemory: 20mb   (실제 필요량 대비 20~60배 여유 — 기존 100mb의 1/5)
mem_limit: 40m    (= 20mb 데이터 + 20mb 오버헤드·AOF COW 여유)
```

기존 150m 대비 **110 MiB를 절약**해 App 쪽 예산으로 돌린다. 오버헤드 여유도 50→20MiB로
줄였는데, 데이터 상한 자체가 100→20mb로 줄면 `BGREWRITEAOF` 시 fork로 복사될 수 있는
최대량(dirty page COW 상한)도 그만큼 작아지기 때문이다.

> 이 20mb/40m은 **실제 가입자·토큰 발급량 실측이 아니라 "캡스톤 프로젝트라 매우 적다"는
> 진술에 근거한 추정치**다. 실제 활성 사용자 수를 알게 되면 다시 산출해야 한다.

## 2.3 App `mem_limit` — 호스트 보호가 최우선 기준

### 왜 "피크 × 마진" 대신 "물리 예산 분할"인가

통상 컨테이너 메모리 상한은 관측 피크의 1.3~1.5배로 잡는다. 실측 피크는 다음과 같다.

| 소스                                           |             값 | 조건                                               |
|----------------------------------------------|--------------:|--------------------------------------------------|
| 운영 cgroup 직접 실측(장시간 구동)                      |     512.6 MiB | swap 없음, 수 시간 구동 후                               |
| CloudWatch 3일 시계열 최댓값(`procstat_memory_rss`) |     509.5 MiB | swap 없음, 3일 관측                                   |
| RAM+swap 합계 최댓값(swap 적용 후 19시간 관측)           | **728.5 MiB** | swap 있음 — "swap이 없었다면 RAM에 그대로 남았을 값"에 더 가까운 추정치 |

이 피크에 1.3~1.5배를 적용하면:

```
512.6 × 1.3~1.5 =  666~ 769 MiB
728.5 × 1.3~1.5 =  947~1093 MiB   ← 물리 메모리(913 MiB) 자체를 넘는다
```

**이 인스턴스에서는 "피크 × 마진" 원칙을 문자 그대로 지킬 물리적 여유가 없다.** 앱의 진짜
수요(swap-free 기준 추정 ~700~730 MiB)가 이미 물리 메모리에 육박하기 때문이다.

`★ 목표를 다시 정의한다 ─────────────────────────`

그래서 기준을 바꾼다. "앱이 얼마나 편하게 동작하는가"가 아니라 **"모든 컨테이너가 동시에
최대치를 써도 호스트가 메모리 부족에 빠지지 않는가"**를 1순위로 둔다. 27시간 livelock의
근본 원인이 "컨테이너 하나가 호스트 예산을 초과 압박했다"였으므로, 재발 방지의 핵심은
앱의 여유가 아니라 **호스트 천장이 물리 메모리를 넘지 않는 것**이다.

`─────────────────────────────────────────────────`

### 물리 예산을 엄격히 분할

```
t3.micro 가용 물리 메모리     913 MiB
− OS + dockerd (고정비)      230 MiB
− Redis mem_limit(2.2 재산정)  40 MiB
──────────────────────────────────
= App에 배정 가능한 최대       643 MiB   → 640m으로 반올림
```

**검증**: `230 + 40 + 640 = 910 MiB ≤ 913 MiB` — 천장 합계가 처음으로 물리 메모리를 넘지
않는다(여유 3 MiB — 매우 빠듯하므로, 더 안전하게 가려면 App을 630m으로 낮춰 여유를
10 MiB로 늘리는 것도 검토할 수 있다).

### 이 선택이 뜻하는 것 — swap이 예전 계획보다 더 자주 쓰인다

640m은 앞서 계산한 진짜 수요 추정치(swap-free 기준 ~700~730 MiB)보다 **작다.** 실수가
아니라 의도된 결과다 — 앱이 640m을 넘어서려 하면 그 초과분(약 60~90 MiB)은 호스트를
압박하는 대신 **swap으로 넘어간다.**

1부(1.2절)에서는 "swap은 평소엔 안 쓰이는 최후의 안전판이어야 한다"고 했는데, 이번 선택은
그 원칙과 약간 부딪힌다 — swap이 비상용이 아니라 어느 정도 **일상적으로 초과분을 받아주는
역할**을 하게 된다. 이 트레이드오프를 받아들이는 이유는, 지금 우선순위가 "응답 속도"가
아니라 "호스트가 절대 안 죽는 것"이기 때문이다. 성능(잦은 스와핑으로 인한 GC·응답 지연)을
다소 희생해서라도 호스트 안정성을 확정 짓는 쪽을 택했다.

`640 / 512.6 = 1.25배`로 통상 권장 범위(1.3~1.5배) 하한보다도 약간 낮다 — 이 역시 같은
이유다. 실측 피크 대비 마진을 넉넉히 주는 것보다, 호스트 예산 안에 확실히 들어오는 걸
우선했다.

## 2.4 호스트 예산 — 처음으로 오버커밋이 사라졌다

```
천장 합계: OS 230 + Redis 40 + App 640 = 910 MiB  vs 물리 913 MiB → 99.7%
```

기존 700m/150m 조합은 `1080/913=118%`로 오버커밋 구조였다(swap이 그 초과분을 흡수하는
설계). 이번 640m/40m 조합은 **천장 합계 자체가 물리 메모리 안에 들어온다** — 모든
컨테이너가 동시에 각자의 상한까지 써도 호스트 자체는 메모리 부족에 빠지지 않는다는
뜻이다. 다만 여유가 3 MiB뿐이라 매우 빠듯하다.

swap의 역할도 이제 달라진다 — 오버커밋을 완충하는 게 아니라, **앱 혼자만의 진짜 수요 중
640m을 넘는 부분을 흡수하는 역할**이다.

## 2.5 JVM 힙 비율 — 기본 ergonomics를 그대로 쓴다

힙 상한을 별도 플래그로 지정하지 않고, Java 21의 컨테이너 인식 기본값(`MaxRAMPercentage`
25%)을 그대로 쓴다. `mem_limit=640m` 기준 힙 상한은 **160 MiB**(640의 25%)로 계산된다.

로컬 NMT 실측상 힙 **사용량**은 idle 기준 약 68 MiB(eden 19.9 + tenured 48.3)뿐이다.
160 MiB로도 2.3배 여유이므로 비율을 더 높일 실익이 없다. 만약 비율을 임의로(예: 50%)
올린다면 640m 기준 힙 상한이 320 MiB로 커지는데, `MaxRAMPercentage`는
**힙 상한만 정할 뿐 논힙을 위해 아무것도 예약하지 않으므로**, 이건 논힙 몫을 남겨주는 게
아니라 단순히 필요 이상으로 힙을 부풀릴 여지를 열어주는 것뿐이다. 로컬 실측이 보여주는 위험은
늘 상한이 없는 논힙(≈197 MiB)에서 왔지 힙에서 온 적이 없으므로, 기본값을 그대로 쓰는 편이
근거에 부합한다. 초기 힙 비율(`InitialRAMPercentage`)도 기본값(1.5625%)을 쓴다 — 임의로
높이면 부팅 시점에 불필요한 메모리를 미리 커밋해 RSS를 앞당겨 부풀리기만 한다.

함께 사용하는 다른 JVM 플래그는 힙 비율과 무관한 별개 목적이다.

| 플래그                           | 목적                                               |
|-------------------------------|--------------------------------------------------|
| `-XX:+ExitOnOutOfMemoryError` | 힙 고갈 시 매달리지 않고 즉시 종료 → `restart:always`로 깔끔히 재기동 |
| `-XX:TieredStopAtLevel=1`     | C2 JIT 생략으로 기동 CPU 버스트·코드캐시 절감                   |

**하지 않는 것 — `-XX:MaxMetaspaceSize` 등 논힙 상한 지정**: 실측상 Metaspace
committed(약 90 MiB)가 안정적이고 폭주 증거가 없어, 근거 없는 선제적 안전장치는 넣지 않는다.
실측으로 성장이 확인되면 그때 추가한다.

## 남은 공백

- **모든 실측이 무트래픽 조건이다.** 유저 0명·GPS 0건·외부 요청 0건인 idle 상태의 값이다.
  실트래픽에서 힙 160 MiB가 충분한지는 측정된 바 없다.
- **힙 커밋량을 직접 확인하지 못했다.** `eclipse-temurin:21-jre`에 `jcmd`가 없어 힙/논힙
  분해가 불가능했고, 고정 바닥(≈270 MiB, 로컬 216 MiB에서 성장)은 "힙이 상한까지
  커밋됐다"는 가정 위의 값이다.
- **바닥의 성장 상한을 모른다.** swap 적용 후 19시간 관측한 RAM+swap 합계가 638~729 MiB
  밴드에서 오르내리는 건 확인했지만, 더 긴 시간에 걸쳐서도 이 밴드를 유지하는지는 계속
  지켜봐야 한다.
- **Redis 20mb/40m은 실제 가입자·토큰 발급량 실측이 아니라 "캡스톤 프로젝트라 매우
  적다"는 진술에 근거한 추정치다.** 실제 활성 사용자 수를 확인하면 재산출이 필요하다.
- **640m은 이미 진짜 수요(~700~730 MiB 추정)보다 작게 잡은 값이라, swap을 일상적으로
  쓰는 게 예상된 정상 동작이다.** 이 설계에서 위험 신호는 "swap을 쓴다" 자체가 아니라
  `restart:always`로 인한 **컨테이너 재시작 빈도**다. 이 불확실성은 **swap(익명 페이지
  회수 가능화) → `ExitOnOutOfMemoryError`(깔끔한 종료) → `restart:always`(즉시 재기동)**
  3중 안전망으로 흡수한다. 640m이 부족해도 결과는 장시간 응답불능이 아니라 수 초짜리
  재기동이다. 재시작이 잦게 관측되면 그 자체가 재산출 신호다.

## 검증 방법

```bash
# swap이 활성화되고 fstab에 영속화됐는지
swapon --show
findmnt --verify --verbose

# 힙 비율 플래그가 빠지고 나머지는 남았는지
docker exec myapp cat /proc/1/cmdline | tr '\0' ' '
#   → java -XX:+ExitOnOutOfMemoryError -XX:TieredStopAtLevel=1 -jar app.jar

# mem_limit이 cgroup에 반영됐는지
docker exec myapp cat /sys/fs/cgroup/memory.max
#   → 671088640 (640m)
docker exec redis cat /sys/fs/cgroup/memory.max
#   → 41943040 (40m)

# 투영이 맞았는지 (적용 수 시간 후)
docker exec myapp cat /sys/fs/cgroup/memory.current
#   → 443 MiB 근처 기대(270 바닥 + 160 힙 + 13 file·kernel). 바닥이 더 자라 640m에
#     근접하면 swap 사용량이 함께 늘어나는지 확인 — 그 자체는 정상 동작이다.
```

CloudWatch `procstat_memory_rss`, `swap_used`로 수 시간~1일 추이를 관찰한다. 이번 설계에서
swap은 "평소 0에 가까워야 정상"이 아니라 **어느 정도 지속적으로 쓰이는 게 예상된 동작**이므로,
확인할 것은 swap 크기가 아니라 **① `restart:always`로 인한 재기동 빈도**(잦으면 640m이
부족하다는 신호)와 **② swap 사용량이 무한정 계속 늘어나기만 하는지**(늘어나기만 하면 바닥
자체가 아직 안 멈췄다는 신호)다.
