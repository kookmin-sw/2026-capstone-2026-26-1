# 보호자 위치 조회 화면 진입시 위치 최신화를 위한 보호대상자의 위치 전송 주기 단축

보호자가 피보호자의 위치를 확인하는 순간에도 위치가 3분 전 데이터에 머무르는 구조적 한계를
발견하고, 서버가 클라이언트(Android)에게 능동적으로 신호를 보낼 채널이 아예 없다는 더 근본적인
문제까지 파고들어 FCM 기반의 양방향 트리거 구조를 설계·구현한 과정을 정리한다.

## 문제 상황

"길벗"은 보호대상자의 위치를 주기적으로 수집해 보호자에게 보여주는 서비스다. Android
클라이언트는 "마지막 전송 후 3분이 지났을 때" 또는 "좌표가 20개 이상 쌓였을 때" 둘 중
하나라도 먼저 충족되면 배치 전송하는 조건으로 동작한다.

보호자는 보호 대상자의 최신 위치를 실시간으로 확인하고 싶어하지만 보호 대상자의 안드로이드
기기는 수집된 위치 데이터들을 모아서 서버로 3분에 한번씩 전송한다.

단순히 "위치 데이터 서버 업로드 주기를 아예 짧게 만들자"는 대안은 바로 배제했다.
상시 짧은 주기로 업로드하면 보호대상자 기기의 배터리 소모가 늘어나고, 보호자가 화면을 보지 않는 대부분의 시간에는 그
짧은 업로드 주기가 불필요하다. 그래서 "보호자가 실제로 보고 있는 동안만" 일시적으로 주기를 당기는 것이
맞는 방향이라고 판단했다.

이 방향으로 코드베이스를 살펴보다가 더 근본적인 제약을 발견했다. 서버 → 보호자 방향으로는
이미 SSE 구독(`GET /api/care/dependents/stream`)이 존재해 위치 갱신을 실시간으로 push 하고
있었지만, 서버 → 피보호자(Android) 방향으로 "지금부터 더 자주 보내라"는 신호를 보낼 채널이
프로젝트 전체에 전혀 없었다. FCM이나 WebSocket 관련 의존성도, 관련 코드도 없었다. 즉 이번
작업의 진짜 문제는 "주기를 어떻게 계산할까"가 아니라 "서버가 클라이언트에게 능동적으로 신호를
보낼 수 있는 채널 자체를 새로 놓아야 한다"는 것이었다.

## 해결 방법

### 대안 1: 신호 전달 채널 — 응답 필드 재사용 vs FCM 신규 도입

- **대안 1-1: 기존 GPS 업로드 응답에 필드 추가.** 피보호자가 3분마다 이미 호출하고 있는
  `POST /api/day-routes/{date}/gps-points:batch`의 응답에 "다음 권장 전송 주기" 같은 필드를
  얹는 방식. 새 인프라가 전혀 필요 없어 구현이 가장 가볍다는 장점이 있었다.
- **대안 1-2: FCM data message로 즉시 push.** Firebase Admin SDK를 새로 도입해 서버가 원하는
  시점에 바로 신호를 보내는 방식.

대안 1-1은 구조적으로 치명적인 지연이 있었다. 보호자가 화면에 들어간 순간부터 피보호자의
다음 업로드 주기(최대 3분)가 돌아올 때까지는 여전히 반응이 없다 — "지금 보려고 하는데 아직도
안 빨라졌다"는 경험이 된다. 즉각성이 이번 기능의 핵심 가치였기 때문에, 신규 인프라 도입
비용을 감수하더라도 **FCM(대안 1-2)** 을 선택했다.

### 대안 2: "보고 있음" 상태 판단 — 전용 API 신설 vs 기존 SSE 재사용

FCM을 언제 쏠지 결정하려면 "지금 보호자가 보고 있는가"를 서버가 알아야 한다.

- **대안 2-1: 화면 진입/이탈 전용 API 신설.** 보호자 앱이 위치 조회 화면에 들어오고 나갈 때마다
  명시적으로 호출하는 API를 새로 만드는 방식.
- **대안 2-2: 기존 SSE 구독 연결 자체를 신호로 재사용.** 보호자가 위치 갱신을 실시간으로 받기
  위해 이미 맺고 있는 SSE 커넥션의 연결/해제 생명주기를 그대로 "보고 있음/아님" 신호로 쓰는 방식.

대안 2-1은 화면 상태를 더 정교하게 구분할 수 있지만, 이미 같은 목적(보호자가 지금 보고
있다는 사실)을 담고 있는 연결이 있는데 API 표면을 하나 더 늘리는 건 불필요한 중복이라고
판단했다. `CareSseEmitterRegistry`가 이미 `onCompletion`/`onTimeout`/`onError` 콜백으로
연결 해제 시점을 정확히 알고 있었으므로, **대안 2-2(기존 SSE 재사용)** 로 결정했다.

이 결정을 내부적으로 재검토하는 과정에서 한 번 흔들린 지점이 있었다. "REST 조회 API를 호출할
때마다 발송하면 더 단순하지 않을까"라는 대안을 잠깐 검토했는데, 이 방식은 "원래 주기로 언제
되돌릴지"를 알려줄 신호가 사라진다는 문제가 있었다. 조회는 호출됐다 안 됐다 할 뿐 "그만 보고
있다"는 시점을 명시적으로 알 수 없기 때문이다. SSE 연결 해제라는, 이미 명확한 생명주기 이벤트를
버리고 상태 없는(stateless) 방식으로 갈 이유가 없다고 결론 내리고 원래 설계로 되돌렸다.

### 대안 3: 여러 보호자가 동시에 볼 때의 상태 관리 — 단순 플래그 vs Redis Set 카운팅

한 피보호자를 보호자 여러 명(예: 자녀 두 명)이 동시에 볼 수 있다는 점도 고려해야 했다. 한
명이 화면을 닫아도 다른 한 명이 여전히 보고 있다면 아직 주기를 원래대로 되돌리면 안 된다.

- **대안 3-1: 단순 boolean 플래그.** 누군가 보기 시작하면 true, 아무나 한 명이라도 나가면 false로 뒤집는 방식.
- **대안 3-2: Redis Set으로 watcher 수를 카운팅.** 피보호자 ID별로 Redis Set(`watch:dependent:{id}`)에 보고 있는 보호자
  ID들을 담고, 그 크기로 판단하는 방식.

대안 3-1은 다중 보호자 상황에서 명백히 틀린 동작을 한다. 대안 3-2를 선택하고, **SADD 결과
집합의 크기가 정확히 1이 되는 순간(최초 watcher)에만 단축 신호를, SREM 후 크기가 0이 되는
순간(마지막 watcher)에만 복구 신호를 보내도록** 구현했다. Redis는 이미 이 프로젝트에서
RefreshToken 저장 용도로만 쓰이고 있었는데, TTL이 필요 없는 이 카운팅에도 정확히 들어맞는
자료구조였다.

### 대안 4: FCM이 실어 보내는 값 — 구체적 초 단위 값 vs boolean 상태만

처음에는 `intervalSeconds` 필드에 서버가 "30초로 줄여라", "180초로 복구해라"처럼 구체적인
숫자까지 지시하도록 만들었다. 그런데 이렇게 하면 실제 단축 주기 값을 튜닝할 때마다(배터리
소모 이슈로 더 늘리거나 줄일 때) 백엔드 재배포가 필요해진다는 점이 마음에 걸렸다. 서버가
알아야 할 사실은 "지금 보고 있는 사람이 있다/없다"뿐이고, "그래서 몇 초로 할지"는 온전히
클라이언트 쪽 정책이어야 한다고 판단해, **`intervalSeconds` 숫자 대신 `watching` boolean만
전달**하도록 최종 설계를 수정했다. 서버-클라이언트 책임 경계를 명확히 나눠, 정책 변경이
클라이언트 자체 배포만으로 가능하게 만드는 선택이었다.

### 최종 구조

```
[피보호자 Android]                         [백엔드]                          [보호자 Android]
                                                                              
   위치 배치 업로드                                                             
   POST /day-routes/{date}/gps-points:batch                                  
        │                                                                    
        ▼                                                                    
   DayRouteFacade.uploadGpsPoint()                                           
        │                                                                    
        ├─ LatestGpsPointService (최신 좌표 upsert)                            
        │        │                                                          
        │        ▼                                                          
        └─ CareLocationSseEventService ──── SSE push ──────────────▶ 위치 갱신 실시간 반영
                                                                              
                                             ▲                    
                                             │ SSE 구독 시작/종료          
                                             │ GET /dependents/stream    
                                    CareSseEmitterRegistry                   보호자가 화면 진입/이탈
                                    .register() / .remove()  ◀───────────────────────┘
                                             │
                                             ▼
                                    DependentWatchService
                                    (Redis Set: watch:dependent:{id})
                                             │
                                    SADD 결과 크기 1(최초) → watching=true
                                    SREM 결과 크기 0(마지막) → watching=false
                                             │
                                             ▼
                                       FcmClient
                                    (Firebase Admin SDK)
                                             │
   ◀─────────────────────────────── FCM data message ─────────────────────────
   { "type": "TRACKING_INTERVAL_CHANGE",
     "watching": "true"/"false"
   }
   Android가 자체 정책으로 실제 업로드 주기(초 단위) 결정
```

- **피보호자 → 서버 구간**: 기존 배치 업로드 흐름은 그대로 두고, 그 최신 좌표를 보호자에게
  실시간으로 넘겨주는 기존 SSE 파이프라인도 손대지 않았다.
- **보호자 → 서버 구간**: 이미 존재하던 SSE 연결의 생명주기(연결/해제)를 상태 신호원으로
  재사용해, 새로운 화면 상태 관리 API를 만들지 않았다.
- **서버 → 피보호자 구간**: 이번에 새로 놓은 유일한 신규 채널. Redis Set 기반 watcher 카운팅으로
  "몇 명이 보고 있는가"를 판단하고, 상태가 바뀌는 시점(0→1, 1→0)에만 정확히 한 번씩 FCM을
  발송한다. 서버는 boolean 상태(fact)만 전달하고, 실제 주기 값(policy)은 클라이언트가 결정한다.
- FCM 발송 실패는 예외를 던지지 않고 로그만 남기도록 격리했다. 이 기능은 SSE 연결이라는 핵심
  흐름 위에 얹힌 부가 기능이므로, 부가 기능의 오류가 핵심 흐름(위치 실시간 갱신)을 절대
  막아서는 안 된다고 판단했기 때문이다.

## 결과 및 개선사항

남은 한계와 다음 개선 방향은 다음과 같다.

- SSE 연결 레지스트리가 인메모리 구조라 서버를 다중 인스턴스로 확장하면 특정 인스턴스에만
  연결이 존재하는 한계를 그대로 상속받는다. 트래픽이 늘면 Redis Pub/Sub 기반 브로드캐스트로
  전환을 검토할 계획이다.
- FCM 발송 실패가 로그로만 남고 별도 모니터링 지표가 없다. 운영 단계에서는 발송 실패율을
  관측할 수 있는 메트릭을 추가하는 게 트러블슈팅에 유리하다.
