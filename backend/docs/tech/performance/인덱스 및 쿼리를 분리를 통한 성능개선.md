### 1. 문제 상황

- gps_point 테이블엔 (day_route_id, recorded_at)으로 유니크 인덱스를 걸어놓았다.
- day_route 단건 조회 시에는 연관된 gps_point의 리스트를 함께 응답해준다. 따라서 day_route와 gps_point를 jpa의 fetch join을 이용하여
  db에서 함께 조회하는 쿼리를 작성했다.

    ```java
    @Query("""
            select distinct dr
            from DayRoute dr
            left join fetch dr.gpsPoints gp
            where dr.id = :dayRouteId
                and dr.user = :user
        """)
    Optional<DayRoute> findByIdAndUserWithGpsPoints(@Param("dayRouteId") Long DayRouteId,
        @Param("user") User user);
    ```


- gps_point는 recorded_at으로 정렬한 채로 list에 저장해야했기에 dayRoute 엔티티에는 다음과 같이 `@OrderBy` 를 붙여줬다.

    ```java
    @OneToMany(mappedBy = "dayRoute")
    @OrderBy("recordedAt ASC")
    private List<GpsPoint> gpsPoints;
    ```


- gps_point는 day_route_id를 기준으로 조인되고 recorded_at으로 정렬까지 하니 (day_route_id, recorded_at)의 복합 인덱스를 탈
  것이라고 생각했다.

- 하지만 쿼리 실행계획을 확인해보니 정렬이 인덱스 단에서 해결되지 않고 따로 임시 테이블과 filesort가 붙은 것이 확인되었다.

### 2. 배경 분석

- 쿼리

```sql
select dr1_0.day_route_id,
       dr1_0.bookmarked,
       dr1_0.date,
       dr1_0.deleted,
       dr1_0.end_time,
       gp1_0.day_route_id,
       gp1_0.gps_point_id,
       gp1_0.latitude,
       gp1_0.longitude,
       gp1_0.recorded_at,
       dr1_0.memo,
       dr1_0.start_time,
       dr1_0.total_distance,
       dr1_0.user_id
from day_route dr1_0
         left join
     gps_point gp1_0
     on dr1_0.day_route_id = gp1_0.day_route_id
where dr1_0.day_route_id = 1
  and dr1_0.user_id = 1
order by gp1_0.recorded_at;
```

- 쿼리 실행계획

|    |             |       |            |       |                          |                          |         |       |      |          |                                     |
|----|-------------|-------|------------|-------|--------------------------|--------------------------|---------|-------|------|----------|-------------------------------------|
| id | select_type | table | partitions | type  | possible_keys            | key                      | key_len | ref   | rows | filtered | Extra                               |
| 1  | SIMPLE      | dr1_0 | NULL       | const | PRIMARY,uk_user_date     | PRIMARY                  | 8       | const | 1    | 100      | **Using temporary; Using filesort** |
| 1  | SIMPLE      | gp1_0 | NULL       | ref   | uk_day_route_recorded_at | uk_day_route_recorded_at | 9       | const | 80   | 100      | NULL                                |

gps_point 테이블에서 day_route_id로 필터링하는 과정에서 복합인덱스가 사용되었다. 그리고 테이블을 모두 조인하여 결과를 만든 다음에 별도의 정렬 작업이 발생했다.
즉 복합 인덱스에서 day_route_id만 조회에 사용되었고 recorded_at은 사용되지 않은 것이다.

**left join에서 정렬 기준 컬럼이 드리븐 테이블에 있다면 filesort가 발생한다.**

문제는 left join에 있었다. 우리 쿼리의 드라이빙 테이블은 day_route이고, 드리븐 테이블은 gps_point이다. 조인 시 gps_point의 데이터가 null일
수도 있다. 따라서 db는 따로 드라이빙 테이블의 결과를 임시 테이블에 저장해서 결과셋을 모은 다음에 별도의 정렬 작업을 진행하게 된다.

인덱스 단에서 정렬을 해결하려면 정렬 기준 컬럼이 드라이빙 테이블에 있어야 한다.

### 4. 해결 방법

드리븐 테이블인 gps_point에 정렬 기준 컬럼이 있는 한 인덱스에서 정렬을 해결할 수 없다.

쿼리 한 번에 dayRoute와 gpsPoint를 조인해서 가져오는 것에서 dayRoute 단건 조회+gpsPoint N건 조회로 쿼리를 2번으로 나눠보내는 것으로 변경했다.

특히 gps_point는 row수가 많을 확률이 크다. 그럼 조인 테이블도 커질거고 여기서 별도의 정렬 작업을 거칠바엔 쿼리를 2번 나눠보내서 조인을 없애고 인덱스 단에서 바로
정렬을 처리하도록 변경했다.

```java

@Transactional(readOnly = true)
public DayRouteDetailResponse getDayRouteDetail(Long dayRouteId, User user) {
    DayRoute dayRoute = dayRouteRepository.findByIdAndUser(dayRouteId, user)
        .orElseThrow(() -> new BusinessException(DayRouteErrorCode.CANNOT_ACCESS_DAY_ROUTE));

    List<GpsPoint> gpsPoints = gpsPointService.getGpsPointsByDayRouteId(dayRouteId);

    return DayRouteMapper.toDayRouteDetailResponse(dayRoute, gpsPoints);
}
```

테스트 데이터로 day_route 500개와 day_route 하나 당 500개의 gps_point를 DB에 적재하였다.

변경 전 API는 Latency는 274, TPS는 3.50877로 측정됐고 변경 후 API는 Latency는 49, TPS는 19.60784 측정됐다. TPS가 5배정도 올랐다.

### 5. 배운 점

사실 이건 **쿼리 한번에 큰 작업 처리하기 vs 쿼리 2번에 가벼운 작업 처리하기** 이 둘 중 후자를 선택한 것이다. 정렬할 row 수가 많지 않았다면 네트워크를 한 번만 타는
것이 더 나은 선택이었을 수 있지만 gps_point 특성 상 row 수가 많을 확률이 크기 때문에 정렬 비용을 최소화할 수 있게 쿼리를 분리하는 쪽을 선택하였다.

옛날엔 DB에 쿼리가 덜 나가는 쪽이 무조건 유리한 줄 알았는데 꼭 그런 것만은 아니었다. 그리고 인덱스가 성능에 미치는 효과를 체감하게 되었다.
