# 로컬 개발 환경을 네이티브에서 도커 컨테이너로 전환하기

## 한 줄 요약

MySQL·Redis·Spring Boot를 모두 로컬에 직접 설치(네이티브)해 띄우던 개발 환경을,
**DB·캐시만 도커 컨테이너로 옮겨 운영 환경과 버전·설정을 일치시키고, 애플리케이션은
네이티브로 남겨 개발 속도를 지키는 하이브리드 구성**으로 전환했다. 로컬 네이티브 Redis는
운영의 메모리 상한·LRU 축출 정책이 없어 "운영에서만 발생하는 동작"을 재현할 수 없었고,
MySQL도 운영 DB와 버전이 어긋날 위험이 있었다

---

## 1. 문제 상황 — 왜 굳이 바꾸려 했는가

처음 로컬 개발 환경은 **MySQL, Redis, Spring Boot 애플리케이션을 전부 내 OS에 직접 설치해서
띄우는(네이티브)** 방식이었다. 당장 동작에는 문제가 없었기 때문에 "이대로도 충분한가?"를
스스로 점검하던 중, 세 가지 위험을 인지했다.

### (1) 운영 환경과 로컬의 "미묘한 불일치"

우리 서비스는 로그인 시 발급하는 재발급 토큰(RefreshToken)을 Redis에 저장한다. 운영 환경의
Redis는 메모리 상한(100MB)과, 상한을 넘으면 **가장 오래 안 쓴 키부터 자동으로 지우는 정책
(LRU 축출)**이 걸려 있다. 그런데 내 로컬 네이티브 Redis는 이런 상한이 없다. 즉 **운영에서만
발생할 수 있는 "오래된 토큰이 밀려나는" 동작을 로컬에서는 절대 재현할 수 없었다.** MySQL도
마찬가지로, 운영 DB(관리형 서비스)와 내 로컬 MySQL의 버전이 일치한다는 보장이 없어, 특정
버전에서만 다르게 동작하는 SQL 문제를 놓칠 위험이 있었다.

### (2) 포트 충돌

운영 DB에 접속해 데이터를 확인할 때 쓰는 보안 터널이 로컬 3306 포트를 경유하는데, 로컬
네이티브 MySQL이 이미 3306을 점유하고 있어 충돌이 났다. 이건 이전 작업에서 이미 겪어
알고 있던 함정이었다.

### (3) 재현성

새 팀원이 합류하면 "MySQL 몇 버전 깔고, Redis 설정은 이렇게…"를 매번 수동으로 맞춰야 했다.

이 세 가지를 근거로, **"인프라(DB·캐시)를 운영과 동일한 형상으로 코드화해서 재현 가능하게
만들자"**고 판단했다. 단순히 "요즘 도커 쓰니까"가 아니라, 위에서 정의한 구체적 위험을
없애는 것이 목적이었다.

## 2. 해결 방법 — 무엇을 어디까지 컨테이너로 옮길 것인가

### 2-1. 첫 번째 결정: 애플리케이션까지 컨테이너로 넣을 것인가

가장 먼저 부딪힌 판단은 "**Spring Boot 애플리케이션도 컨테이너로 띄울 것인가**"였다.
세 가지 안을 비교했다.

- **대안 1 — 전부 네이티브 유지(현행)**: 위에서 정의한 불일치·재현성 문제가 그대로 남는다. 탈락.
- **대안 2 — 전부 컨테이너화(앱 포함)**: 운영 배포 형상과 가장 가깝다는 장점이 있다. 하지만
  우리 앱의 컨테이너 빌드는 매번 `clean`부터 전체 빌드를 다시 하도록 되어 있어, **코드를 한
  줄 고칠 때마다 이미지를 새로 굽는 비용**이 든다. IDE 디버거를 바로 붙이기도 번거롭다.
  즉 "매일 수십 번 반복하는 코드 수정 루프"가 크게 느려진다.
- **대안 3 — 하이브리드(인프라만 컨테이너 + 앱은 네이티브)**: DB·캐시는 컨테이너로 운영과
  맞추고, 앱은 네이티브로 실행해 즉시 재시작·핫 리로드·디버깅을 유지한다.

**대안 3을 선택했다.** 근거는 명확했다 — 컨테이너화의 목적이 대상마다 다르기 때문이다.
DB·캐시는 **"환경을 운영과 똑같이 재현"**하는 게 목적이라 컨테이너가 정답이지만, 앱은
**"내가 방금 고친 코드를 최대한 빨리 돌려보는 것"**이 목적이라 네이티브가 정답이다. 앱을
컨테이너로 검증하는 건 코드를 짜는 순간이 아니라 배포 직전에 가끔 하면 되는 별개의 작업이다.

이 결정을 실행에 옮길 수 있었던 결정적 이유는, 애플리케이션 설정이 이미 접속 정보(DB 주소,
계정, Redis 주소 등)를 **코드에 박아두지 않고 전부 환경변수로 빼둔** 구조였다는 점이다.
덕분에 **애플리케이션 코드는 단 한 줄도 고치지 않고, 접속 대상 주소만 바꾸면** 네이티브에서
컨테이너로 갈아탈 수 있었다.

### 2-2. 두 번째 결정: 포트 전략 — 기존 네이티브를 끌 것인가

- **대안 1 — 네이티브 서비스를 끄고 표준 포트(3306/6379) 사용**: 설정이 가장 단순하지만,
  기존에 쓰던 네이티브 환경을 매번 껐다 켜야 하고, 3306 포트 충돌 문제도 남는다.
- **대안 2 — 컨테이너를 다른 포트로 띄워 네이티브와 공존**: 기존 환경을 건드리지 않는다.

**대안 2(공존)를 선택**했다. 기존 네이티브 서비스와 보안 터널이 쓰는 포트를 피해,
**MySQL은 3307, Redis는 6380**으로 매핑했다. "기존 것을 깨지 않고 새 것을 옆에 세운다"는
원칙으로, 언제든 안전하게 되돌릴 수 있게 했다.

### 2-3. 최종 설계 구조

핵심은 **"접속 설정값이 여러 곳에 흩어지지 않고, 한 원본(source of truth)에서 흘러가게
만드는 것"**이었다. 최종 구조는 다음과 같다.

```
                      ┌───────────────────────────────────────────┐
                      │  docker-compose.local.yml  (팀 공유·커밋)   │
                      │   - MySQL 8.0  : host 3307 → container 3306 │
                      │   - Redis 7    : host 6380 → container 6379 │
                      │   - 운영과 동일한 Redis 메모리 상한·LRU 정책 │
                      └───────────────────────────────────────────┘
                                        ▲  (컨테이너를 "생성")
                                        │
   [ .env.local ]  ── 단일 원본(값) ────┤
   DB 주소=3307                          │
   DB 계정=gilbut                        ▼  (앱이 그 컨테이너에 "접속")
   Redis 포트=6380          ┌─────────────────────────────────┐
        │                   │  Spring Boot (네이티브 실행)      │
        │                   │   localhost:3307 → 컨테이너 MySQL │
        └── 값 주입 ───────▶│   localhost:6380 → 컨테이너 Redis │
        │                   │   (테스트는 인메모리 H2 → 영향 없음)│
        │                   └─────────────────────────────────┘
        │
        └── 동기화 스크립트 ──▶ [ 개발 도구용 설정 파일 ]
                               (같은 값을 도구 실행 환경에도 주입)
```

- **`docker-compose.local.yml`**: 인프라를 코드로 정의한 파일. 운영 배포용 파일과는 **별도**로
  두었다(운영은 외부 관리형 DB를 쓰므로 구성이 다르다). Redis에는 운영과 **동일한 메모리
  상한·축출 정책**을 명시해, 앞서 문제였던 "LRU 축출을 로컬에서 재현 불가"를 해소했다.
- **`.env.local`(단일 원본)**: 접속 주소·계정 등 실제 값이 담기는 유일한 원본. 이 파일은
  비밀값을 포함하므로 버전 관리에서 제외된다.
- **경계**: 각 구간의 역할이 분리되어 있다. compose 파일은 "컨테이너를 **만드는**" 쪽,
  애플리케이션은 "그 컨테이너에 **접속하는**" 쪽이다. 두 값(생성 시 계정 / 접속 시 계정)은
  반드시 **일치**해야 하며, 그 일치를 한 원본에서 관리한다.

## 3. 결과 및 개선사항

### 검증

설계가 실제로 성립하는지 단계별로 확인했다.

- **인프라 기동**: 컨테이너가 정상(healthy)으로 뜨고, 전용 계정 `gilbut`이 **우리 서비스 DB에
  대한 권한만** 가진 것을 확인했다(다른 DB는 목록에조차 보이지 않음 = 권한 격리 성립).
- **운영 환경 일치**: 컨테이너 Redis의 메모리 상한·LRU 정책이 운영과 동일하게 적용됨을 확인.
- **애플리케이션 연동**: 네이티브로 실행한 앱이 컨테이너 MySQL(3307)에 정상 접속하고, 비어
  있던 컨테이너 DB에 우리 도메인 테이블(12개)이 자동 생성되는 것까지 확인했다. HTTP 요청도
  정상 응답했고, 인증이 없는 보호 API 요청은 의도대로 차단됐다.
- **버그 수정 검증**: 설정 파일에 일부러 잘못된 값을 심어놓고 동기화 스크립트를 돌려,
  `.env.local`의 올바른 값으로 덮여쓰는지(=원본 우선이 실제로 동작하는지) 확인했다. 이어
  실제로 포트를 바꾼 뒤 그 변경이 끝까지 전파되는 것도 재차 확인했다.

검증 중, 설정값이 세 곳(컨테이너 정의·앱 원본·도구 설정)에서 잠깐 어긋나 앱이 옛 포트로
접속을 시도한 시행착오가 있었다. 이를 계기로 오히려 "한 원본에서만 값을 관리해야 한다"는
설계 원칙을 스크립트 수정으로 강제하게 되었다.

### 한계 및 다음 개선

- **설정 결합도**: 현재는 앱 접속값과 컨테이너 생성값을 한 이름으로 묶어 편의를 얻었지만,
  나중에 앱을 컨테이너가 아닌 다른 DB로 붙이는 상황이 오면 이름 공간을 분리하는 편이
  안전하다. 지금 로컬 용도에는 결합이 더 단순해 그대로 두었다.
- **최소 권한 강화**: 전용 계정에 부여한 권한을 실제 앱이 필요로 하는 범위로 더 좁힐 수 있다.

이 작업으로, 로컬에서도 운영과 같은 데이터베이스·캐시 형상을 코드 한 벌로 재현할 수 있게
되었고, "내 환경에서만 되는" 부류의 문제를 사전에 걸러낼 토대를 갖췄다.

> 구현·검증 반복은 AI 페어 프로그래밍 도구(Claude Code)로 가속했으나, 어떤 위험을 왜
> 해결할지, 대안을 어떤 기준으로 고를지에 대한 판단은 위 서술대로 직접 내렸다.
