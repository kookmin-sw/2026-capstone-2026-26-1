### 1. 문제 상황

기존 `GlobalExceptionHandler`에서는 서비스 단에서 발생하는`BusinessException`에 대해서만 핸들링을 하고 있었다.

- dto valid 실패

- 타입 불일치

- json 문법 불일치

위와 같이 사용자가 잘못된 요청을 보낼 시에 전역 예외 핸들러가 동작하여 400 에러 메시지를 응답하지 않고 **모두 서버 내부 예외(500)으로 처리**되었다.

클라이언트가 에러 메시지를 이해하기 쉽도록 예외 상황을 분기하고 에러 응답 메시지의 형식을 통일하고자 했다.

---

### 2. 배경 분석

사용자의 요청 형식이 잘못된 경우 발생하는 예외는 다음과 같다.

- `MethodArgumentNotValidException`: 요청 바디 DTO의 validation이 실패한 경우

- `HttpMessageNotReadableException`: 요청 바디의 json 파싱에 실패한 경우(ex: 숫자 필드에 문자열이 들어옴)

- `MethodArgumentTypeMismatchException`: 메서드 파라미터(**[@RequestParam](https://github.com/RequestParam)
  **,**[@PathVariable](https://github.com/PathVariable)**)의 타입 변환이 실패한 경우

- `ConstraintViolationException`: 메서드 파라미터 검증 실패(**[@RequestParam](https://github.com/RequestParam)
  **,**[@PathVariable](https://github.com/PathVariable)**)

- `Exception`: 그 외 서버 예외는 공통된 에러메시지(500) 응답

---

### 4. 해결 방법

예외 처리 방식의 일관성을 확보하기 위해 다음 목표를 세웠다.

- 모든 에러 응답을 공통 형식으로 통일한다.

- 에러 종류는 `ErrorCode` 기반으로 관리한다.

- 필드 단위 에러가 필요한 경우 `fieldErrors`에 담아 전달한다.

- `GlobalExceptionHandler`에 `MethodArgumentNotValidException` , `HttpMessageNotReadableException` ,
  `MethodArgumentTypeMismatchException` , `ConstraintViolationException` , `Exception` 타입을 처리하는 메서드를
  추가한다.

**공통 에러 응답 형식 정의**

에러 응답을 다음과 같은 필드로 통일하였다.

- `code`: 클라이언트가 에러 종류를 식별하기 위한 값

- `message`: 에러에 대한 공통 설명

- `fieldErrors`: 필드 단위 상세 오류 목록

일반적인 예외는 `fieldErrors`를 빈 리스트로 내려주고, 검증 실패나 특정 필드 형식 오류가 있는 경우에만 값을 채운다.

---

### 5. 결론

이번 트러블슈팅의 핵심은 단순히 예외를 잡는 것이 아니라, **예외를 클라이언트가 이해하기 쉬운 공통 포맷으로 변환하는 구조를 만드는 것**이었다.

특히 아래 세 가지를 명확히 구분한 것이 중요했다.

- DTO 검증 실패: `MethodArgumentNotValidException`

- JSON 파싱/역직렬화 실패: `HttpMessageNotReadableException`

- 요청 파라미터 타입 변환 실패: `MethodArgumentTypeMismatchException`

- 요청 파라미터 검증 실패:  
  `ConstraintViolationException`

이를 각각 전역 핸들러로 분리하되, 최종 응답 형식은 하나로 통일함으로써 API 품질과 유지보수성을 동시에 높일 수 있었다.
