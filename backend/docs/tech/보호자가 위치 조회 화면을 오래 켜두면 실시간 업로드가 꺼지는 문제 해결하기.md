# 보호자가 위치 조회 화면을 오래 켜두면 실시간 업로드가 꺼지는 문제 해결하기

보호자가 피보호자의 실시간 위치를 오래 지켜볼수록 오히려 위치가 최신으로 갱신되지 않는 문제를
다룬다. 원인은 한 곳이 아니라 "서버가 '지금 보고 있다'는 사실을 딱 한 번만 알리고 다시 알리지
않은 점"과 "앱이 똑같은 알림을 다시 받아도 이미 아는 내용이라며 그냥 흘려버린 점"이라는 두
지점에 걸쳐 있었다. 이 두 원인을 어떻게 찾아냈고 서버와 앱을 함께 고쳤는지 정리한다.

## 문제 상황

이 서비스에는 "보호자가 위치 조회 화면을 열고 있는 동안에는 피보호자 앱이 위치를 더 자주
올리도록" 만드는 기능이 있다. 평소 피보호자 앱은 배터리를 아끼기 위해 GPS 좌표를 모아 3분마다
한 번씩 배치로 서버에 올리는데(NORMAL 모드), 보호자가 실시간으로 위치를 확인하려는 순간에는
이 3분 지연이 그대로 "위치가 3분 전 것"이라는 체감으로 이어진다. 그래서 보호자가 조회 화면에
들어오면 서버가 피보호자 앱에 신호를 보내 즉시 업로드 모드(IMMEDIATE)로 전환시키고, 화면을
나가면 다시 NORMAL로 되돌린다.

이 신호 전달 경로는 다음과 같이 설계되어 있었다.

```
보호자 앱 ── SSE 연결 ──▶ 서버 ── FCM 푸시 ──▶ 피보호자 앱
 (조회 화면)              (watch 상태 관리)      (업로드 모드 전환)
```

보호자가 조회 화면에 들어오면 서버와 SSE(Server-Sent Events) 연결을 맺고, 서버는 이때 피보호자
앱에 FCM으로 `watching=true`를 푸시해 즉시 업로드를 켠다. 보호자가 화면을 나가 SSE 연결이
끊기면 `watching=false`를 푸시해 다시 끈다.

문제는 **보호자가 조회 화면을 10분 넘게 계속 켜두면, 정작 실시간으로 보고 있는 도중에 즉시
업로드가 스스로 꺼진다**는 것이었다. 보호자가 오래 지켜볼수록 위치가 최신화되지 않는, 기능
의도와 정반대의 현상이었다.

### 표면 증상이 아니라 근본 원인을 찾기

타임아웃이 발동하는 지점만 놓고 보면 처음엔 클라이언트만의 문제처럼 보였다. 피보호자 앱에는
`watching=false` 신호가 유실될 경우를 대비한 10분짜리 안전장치가 있었다. `watching=true`를
받은 뒤 10분 안에 `watching=false`가 오지 않으면, "신호가 유실됐나 보다" 하고 스스로 NORMAL로
복귀하는 로직이다. 이것만 보면 "타임아웃 값이 너무 짧다"가 결론이 될 수 있었다.

하지만 그 안전장치가 **왜 신호가 유실되지도 않았는데 발동하는가**를 서버 코드까지 내려가
확인한 결과, 원인은 클라이언트가 아니라 서버-클라이언트 사이의 **전제 불일치**였다. 서버의
watch 관리 로직은 SSE watcher 수가 `0→1`로 바뀌는 **최초 시점에 딱 한 번만** `watching=true`를
보내고, 연결이 유지되는 동안에는 아무것도 재발송하지 않았다. 반면 클라이언트의 10분 타임아웃은
"신호가 유실됐을 때"만 가정한 설계였는데, 실제 서버는 **애초에 재발송을 하지 않으므로** 보호자가
멀쩡히 계속 보고 있어도 클라이언트 입장에선 "10분째 아무 신호가 없는" 상태와 구분되지 않았다.
즉 "신호 유실 대비용" 안전장치가, 정상적으로 오래 보고 있는 상황까지 오작동으로 끄고 있었던
것이다.

### 서버만 고치면 안 되는 두 번째 원인

여기서 서버가 주기적으로 `watching=true`를 재발송하게 만들면 될 것 같았지만, 클라이언트 코드를
먼저 살펴보니 **서버만 고쳐서는 여전히 재현되는 두 번째 원인**이 숨어 있었다. 피보호자 앱은
업로드 모드를 `StateFlow`(안드로이드 코루틴의 상태 홀더)로 들고 있었는데, `StateFlow`는 **직전
값과 동일한 값을 다시 넣으면 이를 중복으로 보고 아무 이벤트도 흘려보내지 않는다**(conflate).
이미 IMMEDIATE인 상태에서 서버가 `watching=true`를 다시 보내도, 클라이언트는 "값이 IMMEDIATE →
IMMEDIATE로 그대로네" 하고 조용히 무시해버린다. 결국 재발송이 도착해도 타임아웃 타이머는
리셋되지 않아, 서버만 고쳐서는 문제가 그대로 남을 상황이었다.

이 두 번째 원인을 서버 수정 전에 미리 발견한 것이 이번 작업의 핵심이었다. 한 계층만 고치면
다른 계층 때문에 여전히 실패한다는 걸 확인한 뒤, 두 계층을 함께 수정하는 방향으로 정했다.

## 해결 방법

원인이 두 계층에 걸쳐 있었으므로 해결도 두 갈래로 나눴다. 서버는 "연결이 살아있는 동안
주기적으로 신호를 재발송"하도록, 클라이언트는 "같은 값이 반복 도착해도 매번 반응"하도록
각각 고쳤다.

### 서버 계층 — 재발송을 어떻게 구현할 것인가

우선 안드로이드의 10분 타임아웃 자체를 손대는 대안도 있었으므로, 두 방향을 비교했다.

- **대안 1: 클라이언트의 10분 타임아웃 값을 늘리거나 제거한다.** 서버를 건드리지 않아 가장
  간단하다. 하지만 타임아웃의 원래 목적인 "신호 유실 대비"까지 함께 약해진다. 정말로
  `watching=false`가 유실되는 경우, 즉시 업로드 모드가 무기한 유지되어 배터리와 데이터를
  불필요하게 소모한다. 근본 원인(재발송 부재)은 그대로 둔 채 증상만 가리는 셈이다.
- **대안 2: 서버가 SSE 연결이 살아있는 동안 주기적으로 `watching=true`를 재발송한다.**
  클라이언트의 타임아웃은 "신호 유실 대비"라는 원래 의도 그대로 두고, 근본 원인인 "재발송
  부재"를 서버에서 없앤다. 서버에 주기 작업이 하나 늘어나는 비용이 있다.

타임아웃 안전장치는 그 자체로 올바른 방어 설계였고 문제는 "서버가 재발송을 안 한다"는 쪽에
있었으므로, 증상이 아니라 원인을 없애는 **대안 2를 선택**했다. 재발송 주기는 클라이언트 타임아웃(10분)의
절반인 **5분**으로 잡았다. 재발송이 한 번 유실되더라도 다음 재발송이 타임아웃 전에 도착해
타이머를 리셋할 여유를 두기 위해서다.

재발송을 구현하려면 "지금 watching 중인 피보호자가 누구누구인가"라는 목록이 필요했는데, 기존
상태 구조로는 이걸 바로 뽑을 수 없었다. 서버는 watch 상태를 Redis에 이렇게 들고 있었다.

```
watch:dependent:{피보호자ID}  →  {보호자ID, 보호자ID, ...}   (Set)
```

즉 "이 피보호자를 지금 누가 보고 있는가"는 피보호자ID를 **키 이름에 박아** 관리하는 구조다.
이 방식은 특정 피보호자에 대한 조회에는 빠르지만, "지금 watching 중인 피보호자 전체"를 얻으려면
`watch:dependent:*` 패턴에 매칭되는 모든 키를 훑어야 한다. 운영 환경에서 `KEYS`는 전체
키스페이스를 블로킹하며 스캔해 금지되고, `SCAN`도 5분마다 반복 실행하기엔 규모가 커질수록
비용이 늘어난다.

그래서 **현재 watching 중인 피보호자ID 전체를 담는 별도의 Set을 하나 더** 두기로 했다.

```
watch:active-dependents  →  {피보호자ID, 피보호자ID, ...}   (Set, 시스템 전체에 하나)
```

이 Set은 이미 존재하던 상태 전이 시점 — 최초 watcher가 등록되어 `watching=true`를 보내는
순간과, 마지막 watcher가 해제되어 `watching=false`를 보내는 순간 — 에 한 줄씩만 함께 갱신하면
되므로 쓰기 비용이 거의 없다. 대신 5분 재발송 스케줄러는 이 Set 하나만 조회(`SMEMBERS`)하면
재발송 대상 전체를 O(1)에 가깝게 얻는다.

이것은 "쓰기 시점에 약간의 비용을 더 내고, 읽기 시점의 비용을 스캔에서 단순 조회로 낮추는"
역인덱스(비정규화) 트레이드오프다. `watch:dependent:{id}`가 "피보호자 → 보호자들" 방향이라면,
`watch:active-dependents`는 그 파생 정보인 "watching 중이라는 조건 → 피보호자들"을 미리 계산해
둔 것이다. Redis처럼 패턴 매칭 쿼리가 약한 저장소에서 특히 유효한 방식이다.

최종 서버 구조는 다음과 같다.

```
[SSE 연결 생성]  최초 watcher 등록
   ├─ watch:dependent:{id} 에 보호자ID 추가 (size 0→1)
   ├─ watch:active-dependents 에 피보호자ID 추가   ← 재발송 인덱스 갱신
   └─ FCM watching=true 발송

[5분 주기 스케줄러]  (기존 하트비트 스케줄러와 동일한 패턴)
   ├─ SMEMBERS watch:active-dependents 로 대상 전체 조회
   └─ 각 피보호자에게 FCM watching=true 재발송
        (한 명의 조회/발송 실패가 나머지를 막지 않도록 사용자 단위로 예외 격리)

[SSE 연결 종료]  마지막 watcher 해제
   ├─ watch:dependent:{id} 에서 보호자ID 제거 (size 1→0)
   ├─ watch:active-dependents 에서 피보호자ID 제거  ← 인덱스 정리
   └─ FCM watching=false 발송
```

주기 실행 인프라는 새로 만들지 않았다. 이 서비스에는 이미 SSE 스트림 keep-alive용 하트비트
스케줄러가 동일한 패턴(`@Scheduled(fixedDelayString=...)`)으로 돌고 있어서, 재발송 스케줄러도
같은 관례를 그대로 따라 코드베이스의 일관성을 유지했다.

### 클라이언트 계층 — 같은 값이 와도 반응하게 만들기

클라이언트의 숨은 원인은 `StateFlow`의 값 중복 제거였다. `StateFlow`는 "현재 값이 무엇인가"를
표현하는 데는 이상적이지만("화면에 지금 IMMEDIATE라고 표시"), 이번처럼 **"같은 값이 다시
도착했다는 사실 자체가 의미 있는" 신호**(재발송 = 타이머 리셋 트리거)에는 맞지 않는다.

그래서 업로드 모드를 들고 있는 상태 홀더에, 값 비교 없이 매 호출마다 이벤트를 흘려보내는
`SharedFlow` 채널(`watchingSignalEvents`)을 하나 더 두었다. "현재 모드 스냅샷"이 필요한 기존
소비자는 그대로 `StateFlow`를 쓰고, "매 신호마다 타이머를 리셋해야 하는" 타임아웃 로직만 이
새 채널을 구독하게 분리했다. 이벤트성 신호에는 `StateFlow` 대신 `SharedFlow`를 쓰는 코루틴의
일반적인 관례를 따른 것이다.

여기에 더해, 타임아웃 로직 자체가 안드로이드 `Service` 클래스와 전역 의존성 컨테이너에 강하게
묶여 있어 단위 테스트가 불가능했던 문제도 함께 정리했다. 타임아웃을 스케줄·리셋·취소하는
책임만 떼어 `Service`와 무관한 순수 클래스(`WatchingTimeoutCoordinator`)로 추출하고, `Service`는
이 클래스에 위임만 하도록 바꿨다. 이 리팩터링이 뒤에서 설명할 가상 시간 단위 테스트를 가능하게
했다.

## 결과 및 개선사항

이번 수정에서 가장 검증하고 싶었던 시나리오는 "보호자가 10분 넘게 계속 보고 있어도 즉시
업로드가 꺼지지 않는다"였다. 그런데 이 실기기 종단 검증에는 보호자와 피보호자, 서로 다른 두
계정이 케어 관계로 연결되어 있어야 하는데(서비스 규칙상 자기 자신을 보호자로 지정할 수 없다)
테스트 계정이 하나뿐이라 실기기로는 진행할 수 없었다.

대신 앞서 순수 클래스로 추출해둔 타임아웃 로직을 **가상 시간 기반 단위 테스트**로 검증했다.
코루틴 테스트의 가상 시계(`advanceTimeBy`)로 "5분마다 IMMEDIATE 신호가 반복 도착하는" 상황을
시뮬레이션해, 10분이 지나도 타임아웃이 발동하지 않음을 확인했다. 실제로 10분을 기다려야
확인할 수 있는 시간 의존 로직을, 리팩터링을 통해 밀리초 단위로 검증 가능하게 만든 셈이다.
서버 쪽도 재발송 대상 목록 관리와 부분 실패 격리 동작을 단위 테스트로 덮었고, 기존 SSE/watch
관련 테스트가 회귀 없이 통과하는 것까지 확인했다.

남은 한계와 개선점은 다음과 같다.

- **실기기 종단 검증 미완료.** 두 번째 테스트 계정이 준비되면, 보호자·피보호자를 실제로 케어
  관계로 묶고 조회 화면을 10분 이상 유지하는 시나리오로 종단 검증을 보강할 필요가 있다.
- **재발송 주기와 타임아웃 값의 관계가 코드로 강제되지 않는다.** "재발송 주기(5분) < 타임아웃
  (10분)"이라는 전제가 깨지면 버그가 재발하는데, 지금은 두 값이 서로 다른 계층에 상수로
  흩어져 있어 실수로 어긋날 여지가 있다. 두 값의 관계를 주석이나 검증 로직으로 묶어두면
  안전하다.
- **`watch:active-dependents`에 TTL이 없다.** 지금은 SSE 연결의 정상 종료 콜백들이 모두 상태를
  정리하도록 되어 있어 누수 가능성이 낮지만, 서버 비정상 종료 등으로 해제 로직이 누락되면
  항목이 영구히 남을 수 있다. 다만 TTL은 Redis에서 키 단위로만 걸리고 개별 멤버 단위로는 걸
  수 없어, 그냥 붙이면 오래 보고 있는 정상 상태까지 만료시켜 이번 버그를 Redis 계층에서 그대로
  재현한다. TTL을 쓰려면 5분 재발송 시점에 만료 시간도 함께 갱신하는 설계가 전제되어야 하며,
  이는 "재발송 스케줄러가 멈추면 상태도 함께 사라진다"는 단일 장애점을 하나 더 만드는 트레이드
  오프이기도 하다. 운영에서 상태 누수가 실제로 관측되면 그때 도입할 방어적 개선으로 남겨둔다.
