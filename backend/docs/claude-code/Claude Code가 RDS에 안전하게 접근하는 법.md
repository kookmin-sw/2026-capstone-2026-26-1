# Claude Code가 RDS에 안전하게 접근하는 법

## 요약

운영 RDS(MySQL)는 보안을 위해 퍼블릭 액세스를 차단해뒀다. 운영 DB 데이터 분석을 위해 클로드 코드가 rds의 데이터베이스에
접속할 방법이 필요했다. 나는 Claude Code가 rds에 접근할 때 가장 흔한 "배스천 SSH 터널 + 고정 비밀번호"
방식 대신 SSH 키와 DB 비밀번호를 모두 없앤 IAM 기반 접속 방식을 설계했다.

## 문제 상황

RDS는 퍼블릭 액세스가 차단되어 있어 VPC 외부에서 직접 접속할 수 없었고, 같은 VPC 안에는 SSH로
접속 가능한 EC2 인스턴스가 이미 떠 있었다. 이 EC2를 배스천 삼아 우회 접속하는 것 자체는 자연스러운
선택이었지만, 나는 여기서 멈추지 않고 "이 접속 경로에 어떤 자격증명이 남는가"를 스스로 따져봤다.

가장 먼저 떠오른 방식(`.pem` 키로 SSH 접속 + 읽기 전용 DB 계정의 고정 비밀번호)으로도 기능적으로는
충분했다. 하지만 나는 이 방식에 다음과 같은 구조적 약점이 있다고 판단했다.

- `.pem` 키 파일이라는 물리적 자격증명을 클로드 코드가 읽게 된다. 만약 유출되면
  만료 기한 없이 계속 유효하다.
- 읽기 전용 계정이라도 결국 고정 비밀번호를 갖고, 로테이션·보관이라는 관리 부담이 남는다.

## 해결 방법

두 축으로 대안을 나눠 비교했다: **네트워크 경로**(배스천까지 어떻게 도달할 것인가)와
**DB 인증 방식**(RDS에 어떤 자격증명으로 로그인할 것인가).

**네트워크 경로**

1. **대안 1: SSH 터널** — 배스천에 `.pem` 키로 접속해 로컬 포트 포워딩(`ssh -L`)으로 터널을
   연다. 구성이 간단하지만, 키 파일 관리·22번 포트 노출이라는 약점이 그대로 남는다.
2. **대안 2: AWS SSM Session Manager 포트 포워딩** — 배스천에 인바운드 포트를 전혀 열지 않고도
   IAM 자격증명만으로 세션을 열 수 있고, 세션 시작/종료가 CloudTrail에 남아 감사 추적이
   가능하다.

→ **대안 2(SSM)를 선택**했다. 관리해야 할 물리적 키 파일이 없어지고, 접속 이력이 자동으로 감사 로그에 남는다는 점이 SSH 대비 명확한 우위였다.

**DB 인증 방식**

1. **대안 1: 읽기 전용 계정의 고정 비밀번호** — 구성이 단순하지만, 비밀번호를 어딘가에
   보관해야 하고 로테이션 관리 부담이 남는다.
2. **대안 2: RDS IAM 데이터베이스 인증** — `aws rds generate-db-auth-token`으로 15분짜리
   임시 토큰을 발급받아 비밀번호처럼 사용한다. 클로드 코드가 토큰을 학습하여 어딘가에 남더라도 15분 후 자동
   무효화된다.

→ **대안 2(IAM 인증)를 선택**했다. 고정 비밀번호 대비 유출 위험의 지속 시간을 원천적으로
줄일 수 있다는 점이 결정적이었다.

두 축 모두에서 "관리해야 할 영구 자격증명을 하나도 남기지 않는" 쪽을 선택했다. 다만 이 방식은
사전 설정이 SSH 방식보다 더 필요하다 — 배스천에 SSM 에이전트용 IAM 역할이 붙어 있어야 하고,
RDS에 IAM 인증을 활성화해야 하고, IAM 인증 전용 DB 계정(`IDENTIFIED WITH AWSAuthenticationPlugin
AS 'RDS'`)을 새로 만들어야 한다. 이 초기 구성 비용은 한 번만 지불하면 되고, 이후 접속마다
반복되는 자격증명 관리 부담을 없앨 수 있으므로 충분히 감수할 만하다고 판단했다.

### 최종 설계 구조

최종 설계는 "영구 자격증명이 로컬 어디에도 남지 않는다"는 원칙을 축으로, 네 개의 구성 요소가
각각 하나의 보안 경계를 담당하도록 나눴다.

```
[Claude Code / 로컬 클라이언트]
        │  ① aws ssm start-session (IAM 자격증명으로 인증)
        ▼
[AWS SSM Session Manager]
        │  ② AWS-StartPortForwardingSessionToRemoteHost 문서로
        │     "배스천 → RDS:3306" 구간만 포워딩 (배스천에 인바운드 포트 없음)
        ▼
[배스천 EC2 (SSM 에이전트 + IAM 인스턴스 프로파일)]
        │  ③ VPC 내부 네트워크로만 RDS에 도달 (RDS는 여전히 퍼블릭 액세스 차단 상태 유지)
        ▼
[RDS MySQL] ← ④ aws rds generate-db-auth-token으로 발급한 15분짜리 IAM 토큰으로 인증
             ← ⑤ readonly_iam 계정: SELECT 권한만 보유
```

각 구간이 담당하는 보안 경계는 다음과 같다.

- **① 로컬 ↔ SSM**: 인증의 시작점은 SSH 키가 아니라 IAM 자격증명이다. `ssm:StartSession`
  권한이 없으면 세션 자체가 열리지 않으므로, 이 구간의 신뢰는 전적으로 IAM 정책에 위임된다.
- **② SSM ↔ 배스천**: 포트 포워딩은 "배스천의 22번 포트"가 아니라 "배스천을 경유해 RDS의
  3306번 포트로만" 열리도록 문서(`AWS-StartPortForwardingSessionToRemoteHost`)가 범위를
  제한한다. 배스천 자체의 보안 그룹에는 별도의 인바운드 규칙을 추가할 필요가 없다.
- **③ 배스천 ↔ RDS**: 트래픽은 VPC 내부망을 벗어나지 않는다. RDS의 퍼블릭 액세스 차단 설정은
  이 설계를 도입한 뒤에도 전혀 바뀌지 않았다 — 접근 방식이 늘어난 것이지, 노출 범위가 늘어난
  것은 아니다.
- **④ RDS 인증**: 비밀번호 대신 15분짜리 IAM 토큰을 사용하므로, 이 구간에서 탈취 가능한
  자격증명의 "유효기간"이 사실상 15분으로 제한된다.
- **⑤ 권한 경계**: 설령 앞의 모든 경계가 뚫리더라도, 접속 계정 자체가 `SELECT`만 가진 읽기
  전용 계정이라 데이터 변경/삭제로는 이어지지 않는다.

즉 이 구조는 하나의 강력한 방어선에 의존하는 대신, 네트워크 경로·인증 방식·권한 범위 세 층을
독립적으로 좁혀 어느 한 구간이 뚫려도 피해가 다음 층으로 넘어가지 않도록 설계했다.

## 결과 및 개선사항

최종적으로 로컬 → SSM 포트 포워딩(임시 로컬 포트) → 배스천 EC2 → RDS로 이어지는 경로를 구성했고,
매 접속마다 IAM 토큰을 새로 발급받아 인증하는 방식으로 확정했다. `SELECT 1;`이 정상 반환되는지로
경로 전체(SSM 터널 → IAM 인증)가 의도대로 동작함을 확인했고, 읽기 전용 계정에 `SELECT`만
부여했으므로 `INSERT`/`UPDATE` 시도가 거부되는 것 자체가 "읽기 전용이 실제로 강제되고 있다"는
검증이기도 했다.

이번 설계로 SSH 키와 DB 고정 비밀번호라는 두 종류의 영구 자격증명을 모두 없앴다.

다만 신뢰가 완전히 사라진 것은 아니고 한 단계 옮겨갔을 뿐이다. AWS API(SSM 세션 시작, IAM 인증
토큰 발급)를 호출하려면 결국 로컬에 저장된 IAM 사용자의 액세스 키/시크릿 키를 읽어야 하는데,
이 키는 만료 기한이 없는 고정 자격증명이라 디스크에 평문으로 남아있다. 즉 "DB 계층의 고정
비밀은 없앴지만, AWS 접근 계층의 고정 비밀은 아직 남아 있다"가 정확한 현황이다. 다음 단계로는
장기 IAM 액세스 키 대신 AWS IAM Identity Center(SSO)를 도입해, `aws sso login`으로 발급받는
단기 임시 자격증명으로 전환하는 것을 고려하고 있다 — 이렇게 하면 디스크에 영구히 남는 비밀
자체가 없어진다.
